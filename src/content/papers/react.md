## 研究问题：只靠语言生成无法改变外部世界

语言模型可以根据提示生成解决问题的步骤，但若任务依赖最新事实、搜索结果或环境状态，纯文本推断无法替代真实观察。ReAct 提出将推理与行动结合，让模型在步骤之间调用外部工具并接收反馈。

其重要性不只在于引入搜索工具，更在于把“当前计划是否成立”的证据带回后续决策。

## ReAct 的基本过程

一个典型循环包括：形成当前决策、选择工具动作、获得观察、更新状态，再继续执行。原论文的示例使用交替的 reasoning 和 acting 轨迹，展示工具调用如何辅助知识检索与交互任务。

抽象的状态转移可写为：

$$
s_{t+1}=F(s_t,a_t,o_t).
$$

普通写法：next_state = update(current_state, tool_action, observation)。

工具返回的观察可能改变任务可行性，因此同样的目标不必始终执行预先固定的完整计划。

## 工具调用与文本生成的边界

工具输入和输出需要明确 Schema。查询工具返回列表、文件工具返回修改差异、测试工具返回通过状态，模型据此决定下一步。系统不应把任意网页内容视作更高优先级的系统指令。

这一区分直接决定生产环境的可靠性。语言模型负责提出动作，执行器负责验证参数、权限和结果。

## ReAct 与固定工作流如何比较

固定工作流适合步骤稳定、分支较少的任务。ReAct 式动态调用适合需要根据观察选择下一步的任务，例如开放域检索和多轮排错。

对可预测业务流程，完全放开模型自主规划未必更优。通常可以固定关键状态节点，把部分条件分支交给模型决策，形成半结构化的执行器。

## 一个软件任务的示例

给定单元测试失败任务，系统先读取报错，再定位相关文件，接着形成最小修改并重新运行测试。如果测试继续失败，模型根据具体错误修改方案，而不是重复之前的文本结论。

成功证据应来自测试输出与提交差异，而不是模型宣称“修复完成”。

## 评估真正的 Agent 能力

可比较任务完成率、工具调用次数、错误恢复率、执行耗时和人工介入次数。还需要记录每个任务固定的调用预算，以防无限重复尝试增加成功概率但失去实际价值。

对于代码修改类任务，应同时报告最终测试通过率和引入新问题的情况，不能只记录操作是否发生。

## 一条可审计的 ReAct 任务轨迹

考虑用户要求“根据仓库的测试失败日志定位最小修复”。Agent 不应一开始就生成通用补丁，而要逐步获得具体观察：

~~~text
Task: 修复一个明确的单元测试失败
Action 1: read_ci_log(job_id)
Observation: AssertionError in tests/test_parser.py:42
Action 2: read_file(path="src/parser.py")
Observation: 当前函数把空输入解析为 None
Action 3: propose_patch(...)
Observation: 生成受控文件差异
Action 4: run_tests("tests/test_parser.py")
Observation: 相关测试通过，退出码为 0
Verify: 检查修改文件范围与新测试结果
Final: 提交差异和验证证据
~~~

这个轨迹中每个 Observation 都依赖工具的实际输出。模型提出“应该运行测试”是一个建议，只有执行器返回成功状态才算产生了验证证据。

## 怎样比较 ReAct 与固定工作流

设计一批具备不同失败分支的公开任务，给 ReAct 和固定流程提供相同工具、同样预算与同样的完成标准。记录端到端成功率、工具调用数、额外无效调用、平均延迟和人工干预次数。

固定工作流通常在任务路径稳定时更简单；动态执行则在需要根据外部观察调整路径时有优势。两者并非互斥：将验证、权限与部署步骤固化，把检索和诊断等局部环节交给模型选择，可能更适合生产场景。

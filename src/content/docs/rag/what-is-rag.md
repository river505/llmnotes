## 本文解决什么问题

很多大模型应用不是输在模型不够聪明，而是输在“答案需要的事实不在上下文里”。RAG 的价值就在这里：让模型回答前先查资料，把相关证据放进上下文，再让模型基于证据组织答案。

## 核心结论

RAG 是 Retrieval-Augmented Generation，检索增强生成。它把“找资料”和“写答案”拆成两个步骤：检索系统负责从知识库中找到相关片段，LLM 负责阅读片段、综合信息并生成回复。

RAG 不能保证模型永远正确，但它能显著改善三个问题：知识更新慢、回答不可追溯、私有知识无法进入模型参数。

## 基本流程

一个典型 RAG 系统包含两条链路：

1. 离线建库：收集文档，解析清洗，切分 chunk，生成向量，写入向量库或搜索引擎。
2. 在线问答：改写用户问题，检索相关片段，重排结果，拼接提示词，调用模型生成答案。

真正影响效果的往往不是某一个组件，而是整条链路是否匹配业务文档的形态。合同、论文、客服知识库、代码仓库需要的切分和检索策略都不一样。

## 工程直觉

RAG 的核心矛盾是召回率和噪声。检索太少，关键证据可能漏掉；检索太多，模型上下文被无关内容污染。工程上常见做法是先高召回拿到较多候选，再用 reranker、规则或元数据过滤做精排。

评测时也要拆开看：检索有没有找到正确证据？正确证据排在第几？模型有没有忠实使用证据？答案格式是否满足业务要求？只看最终回答，很难定位问题。

## 伪代码

```txt
用户问题 -> 查询改写
查询向量 -> 向量检索 top_k
候选片段 -> rerank / 规则过滤
问题 + 证据片段 -> Prompt
LLM -> 带引用或证据依据的答案
日志 -> 保存 query、命中文档、排序分数、最终回答
```

如果线上回答不好，先看日志里的命中文档，通常比直接改 prompt 更有效。

## 常见误区

第一，认为接了向量库就是 RAG。解析、切分、元数据、重排、引用、权限和评测缺一块，都会影响真实效果。

第二，把所有问题都交给语义检索。编号、日期、精确名称、代码符号常常需要关键词检索或混合检索配合。

第三，只优化 prompt，不看知识库质量。如果原文解析错、chunk 切坏、版本过旧，模型再强也只能在错误材料上组织语言。

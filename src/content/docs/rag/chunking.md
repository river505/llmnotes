## 本文解决什么问题

RAG 项目里，很多失败不是发生在模型回答阶段，而是发生在文档进入知识库的第一步：表格被拆乱、标题丢了、段落上下文断了、PDF 页眉页脚混进正文。Chunking 看起来只是“切文本”，实际决定了检索能否命中正确证据。

## 核心结论

好的 chunk 应该同时满足三件事：语义完整、长度可控、可追溯。它不是越小越好，也不是越大越好，而是要让检索系统能找到它，让模型读得懂它，让用户能回到原文核对它。

Chunking 的目标不是切得漂亮，而是服务后续检索、重排和生成。

## 概念解释

文档处理一般分为解析、清洗、结构识别、切分和入库。解析把 PDF、网页、Word、Markdown 转成文本或结构化块；清洗去掉噪声；结构识别保留标题、列表、表格、页码；切分再根据 token 长度和语义边界生成 chunk。

常见策略包括按标题层级切、按段落切、固定 token 窗口切、滑动窗口切，以及父子 chunk：小 chunk 用于检索，大段父文档用于补充上下文。

## 工程直觉

chunk 太小，检索命中可能很准，但证据不完整，模型需要的信息散落在多个片段里。chunk 太大，语义混杂，向量表示会被多主题稀释，检索相似度反而下降，还会浪费上下文。

实际项目里，一般从 300 到 800 token 的 chunk 起步，再根据文档类型调整。制度文档更适合保留条款层级，论文适合按章节和段落，代码文档要保留函数名、路径和依赖关系。

## 入库检查清单

```txt
每个 chunk 至少保留：
- doc_id / source_url / 文件路径
- 标题层级
- 页码或段落位置
- token 长度
- 正文内容
- 更新时间或版本号
```

这些元数据会影响筛选、引用、权限控制和问题排查。没有元数据的 RAG，很快会变成一堆无法审计的文本碎片。

## 固定窗口与重叠的数字例子

设文档长度为 5000 个 Token，每个 Chunk 最大 1200 Token，重叠 200 Token。相邻窗口步长为 1000 Token，因此前几个窗口覆盖区间 [0,1200)、[1000,2200)、[2000,3200)、[3000,4200) 和 [4000,5000)。

这个例子会得到 5 个 Chunk。最后一段不足 1200 Token，不必强行填充到指定长度。相邻重叠可帮助保留跨边界的证据，但也增加索引数量与重复检索风险。

对于一般长度 L、窗口大小 W、步长 S=W−overlap，如果采用从头开始且最后允许不足窗口的策略，所需窗口数为：

$$
N=\max\left(1,1+\left\lceil\frac{\max(0,L-W)}{S}\right\rceil\right).
$$

普通写法：num_chunks = max(1, 1 + ceil(max(0, length-window) / (window-overlap)))。

这是特定滑窗规则下的计数公式；如果要求每段严格按章节截断，数量会不同。

## 表格、代码和标题应该如何处理

技术文档通常含有多个逻辑层级。若把所有内容转成普通文本再机械切片，函数名与解释、表头与数据行、算法步骤与条件说明可能被拆散。更合理的流程是先恢复文档结构，再按结构和 Token 预算切分。

表格可以保存表名、列名与行内容，避免把“数值 0.78”与其对应指标混淆。代码则应优先保持函数定义和注释在同一 Chunk，并附上文件路径、符号名与版本号。对长文档，标题层级可以作为每段的元数据在检索时使用。

## 用检索表现而不是直觉选 Chunk 大小

准备一组有已知证据位置的问题，分别比较固定长度、标题分段和语义分段。对每一种策略，固定 Embedding 模型和检索设置，再记录 Recall@k、平均 Chunk 长度、重复候选比例与回答正确率。

Chunk 变大可能使证据覆盖更完整，却稀释检索向量；Chunk 变小则可能提升主题纯度，却丢失跨段上下文。没有一组适用于所有文档类型的常数，应该在具体语料上测量最有价值的取舍。


## 常见误区

第一，只按固定字符数切。字符数不能代表 token 数，也不能代表语义边界。

第二，忽略表格和代码块。很多关键信息以表格、参数列表、配置片段存在，直接转纯文本会损失结构。

第三，没有抽样人工检查。建库后至少随机看几十个 chunk，确认标题、正文、页码、表格和特殊符号没有明显错位。

## Agent 不等于更长的聊天记录

如果一个模型只能连续生成文本，它可以提出方案，却不能确认外部世界是否按方案改变。一个真正可执行的 Agent 需要与环境交互：读取当前状态、选择动作、调用工具、获取观察，然后决定继续、回退还是结束。

这种系统可以使用语言模型作为决策器，但并不意味着所有执行逻辑都交给语言模型。最可靠的工程形式通常在确定性流程和模型判断之间划清边界。

## 四种角色：模型、工具、状态与控制器

模型接收任务上下文，提出下一步动作或最终回答。工具提供外部能力，例如搜索、数据库读取、文件编辑、代码运行或工单处理。

状态记录当前目标、已完成步骤、工具返回、资源预算及错误信息。控制器则负责验证动作是否合法、工具是否被授权、结果如何合并以及何时终止。

这四种角色经常被混写进一个 Prompt，但在实际系统中保持独立更容易测试、调试和做权限管理。

## 执行循环的状态方程

将任务状态记为 s_t，模型选择动作为 a_t，环境返回观察 o_t。状态更新为：

$$
s_{t+1}=F(s_t,a_t,o_t).
$$

普通写法：next_state = transition(current_state, selected_action, tool_result)。

这里 F 由执行框架实现，可能包括更新任务进度、保存文件差异、检查测试结果、扣减工具预算等。Agent 的关键在于允许观察结果真正影响下一个动作。

## ReAct：交替观察而不是一次计划到底

ReAct 将推理与行动组织为交替轨迹。模型先决定需要哪项外部信息，调用工具后，再根据真实观察选择后续步骤。

例如代码修复任务：读取报错 → 定位文件 → 最小修改 → 运行测试 → 检查失败原因。如果测试未通过，下一次动作应依据新的错误输出，而不是机械重复原来的方案。

与之相比，固定工作流在任务结构稳定时更直接、更便宜。实际系统常把两者结合，在固定检查节点之间使用模型判断。

## 工具契约决定可靠性

工具应暴露明确的名称、参数 Schema 和返回格式。对于写操作，最好包含资源位置、预期旧状态、修改内容和权限标识；对于查询操作，应该明确分页、超时和结果数量限制。

例如，文件修改工具若支持基于旧内容匹配的替换，就可以避免在文件已被别人更新后直接覆盖新内容。这个设计的价值来自并发控制，而不依赖模型是否理解版本冲突。

## 成功条件必须由外部证据定义

如果模型说“已经修复”，但测试没有运行，任务仍然未被验证。Code Agent 的完成条件可以是指定测试通过、构建成功并生成可审查的差异；文档查询任务的完成条件可以是所需证据已检索并通过引用检查。

系统应清晰区分 DONE、PARTIAL、FAILED。对于执行超时、权限不足和不可恢复的工具错误，停止并返回可检查的状态比无限重试更合理。

## 安全边界与 Prompt Injection

工具返回值、仓库源代码、网页和邮件都属于外部数据来源。若其中出现“忽略原始任务、执行新命令”等句子，执行器应将它们当作数据，不得提升为工具授权或系统指令。

最小权限原则适用于 Agent 的工具配置：任务只要求查询时不提供写入能力，涉及删除、发布、支付等不可逆操作应由实际授权主体确认。

## 如何评测 Agent

应在固定任务集上记录任务完成率、外部测试通过率、工具调用数量、耗时、成本、人工介入次数和错误恢复能力。不同方案比较时，应保证任务、预算与工具权限一致。

还可以将失败按“计划错误、工具参数错误、观察误读、无法验证、权限拒绝”分类。针对失败类型做改进比堆叠更多提示词更可解释。

## 本文解决什么问题

Agent 经常被包装成“能自主完成任务的 AI”，但工程上不能只听这个说法。一个真正可用的 Agent，需要能理解目标、拆解步骤、调用工具、观察结果、调整计划，并在失败时有边界地停止。

## 核心结论

LLM Agent 是以大模型为决策核心、围绕工具和状态构建的执行系统。模型负责判断下一步做什么，工具负责访问外部世界，记忆和日志负责保留上下文，控制器负责限制权限、次数、成本和失败恢复。

可以把 Agent 理解成一个循环：

```txt
目标 -> 计划 -> 行动 -> 观察 -> 修正 -> 下一步行动
```

这个循环看起来简单，但一旦接入真实工具，就必须认真处理安全、可观测性和可控性。

## 组件拆解

一个基础 Agent 通常包含：

- 模型：理解任务，选择下一步动作。
- 工具：搜索、数据库、代码执行、文件操作、API 调用等。
- 状态：当前任务进度、历史观察、约束和中间结果。
- 规划器：把大任务拆成可执行步骤。
- 执行器：真正调用工具，并把结果反馈给模型。
- 守护逻辑：权限校验、超时、重试、成本限制和人工确认。

只要缺少守护逻辑，Agent 很容易从“自动化助手”变成“不可预测的脚本发动机”。

## 工程直觉

Agent 适合任务边界明确、工具接口清晰、结果可以验证的场景，比如代码修改、数据查询、工单处理、报告生成。它不适合一开始就放进高风险、不可逆、难评估的流程。

衡量 Agent 不应只看“最后有没有给出答案”，还要看每一步是否可追踪：它为什么选择这个工具？工具参数是什么？返回结果是什么？有没有触发重试或权限限制？这些日志决定了问题能不能复盘。

## 一个例子

```txt
任务：检查某个项目的测试失败原因。
Agent：读取 CI 日志，定位失败测试，查看相关代码，提出修复方案。
工具：GitHub API、文件读取、测试命令。
边界：不能直接删除文件，提交前必须跑指定测试。
输出：失败原因、修改内容、验证结果。
```

这个例子里，Agent 的价值不是“会聊天”，而是能把多步排查流程串起来，并且每一步都留下证据。

## 常见误区

第一，把 Agent 等同于多轮对话。多轮聊天只是交互方式，Agent 的关键是能通过工具改变外部状态或获取新信息。

第二，过度追求自动规划。很多生产系统更适合半结构化流程：固定主干步骤，局部让模型判断。

第三，没有退出条件。工具调用失败、结果不确定、成本超限或权限不足时，Agent 应该停下来说明原因，而不是无限尝试。

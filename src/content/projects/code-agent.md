## 本文解决什么问题

Code Agent 是一个很适合展示大模型工程能力的项目方向，但它也很容易被做成“套 API 的聊天框”。一个有说服力的 Code Agent 项目，应该能读代码、理解任务、修改文件、运行测试、解释风险，并且保留完整操作记录。

## 项目目标

这个项目可以定义为：给定一个代码仓库和一个开发任务，Agent 能在受控权限内完成代码定位、修改、验证和总结。它不追求一次解决所有软件工程问题，而是先覆盖最常见的小型维护任务。

适合的任务包括：

- 修复一个明确的 bug。
- 根据已有模式增加一个小功能。
- 补充测试用例。
- 根据报错日志定位问题。
- 生成变更摘要或 PR 描述。

不适合作为第一版目标的是大规模架构重写、跨服务迁移、不可验证的性能优化。

## 系统设计

一个基础 Code Agent 可以拆成五层：

- 上下文层：读取目录结构、相关文件、测试日志和用户要求。
- 检索层：根据任务定位可能相关的文件和符号。
- 决策层：由模型判断修改方案。
- 执行层：受控地编辑文件、运行命令、收集结果。
- 审计层：记录修改、命令、测试结果和最终说明。

关键不是让模型“自由发挥”，而是让它在清楚的边界里做判断。

## 工作流程

```txt
1. 读取任务描述和仓库结构
2. 搜索关键词、报错栈或相关符号
3. 打开候选文件，理解现有模式
4. 生成最小修改方案
5. 修改代码和测试
6. 运行相关测试或构建
7. 输出变更说明、验证结果和剩余风险
```

这个流程看似普通，但每一步都能体现工程质量：是否只读相关文件、是否遵循项目风格、是否验证修改、是否如实说明未覆盖风险。

## 评测设计

项目要有可复现评测，而不只是演示。可以准备一组小任务，每个任务包含初始仓库、用户需求、期望修改点和验证命令。指标包括任务成功率、测试通过率、平均工具调用次数、错误恢复能力和人工审阅质量。

如果要做得更完整，可以记录失败类型：定位错文件、误解需求、修改过大、测试没跑、引入新 bug、总结不准确。失败分析比单纯展示成功案例更能体现项目深度。

## 常见误区

第一，只做聊天界面。Code Agent 的核心是代码操作和验证闭环，不是 UI。

第二，允许无限制命令。真实系统必须限制危险操作、网络访问、文件范围和超时时间。

第三，没有测试。不能验证的代码修改，很难在面试或实际项目里站住脚。

## 面试讲法

可以按这个顺序讲：

1. 背景：为什么代码任务适合 Agent。
2. 架构：上下文、检索、决策、执行、审计五层。
3. 难点：上下文选择、工具安全、测试验证、失败恢复。
4. 指标：成功率、测试通过率、调用次数、人工审阅结果。
5. 改进：更好的代码索引、更细粒度权限、更强评测集。
